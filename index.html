04 · How I work

The SDLC, run properly.

Agile and Scrum by default, with the discipline of a document trail: every requirement has a source, an owner, a test and a change history.

Phase 01

Understand the business before the software

Most failed requirements were never really understood. I start with the people who do the work and the numbers behind the pain.

What I do

  • Run discovery calls and requirements workshops with founders, operations teams and end users
  • Map stakeholders with a RACI and agree who decides what
  • Model the AS-IS process and turn pain points into measured baselines
  • Research compliance for each launch market before design starts
  • Compare competitors and solution options against budget and scope

Techniques

  • Interviews
  • Workshops
  • Document analysis
  • Process walkthroughs
  • Surveys
  • Stakeholder analysis
  • Gap analysis
  • Market research

What it produces

Phase 02

Turn needs into testable requirements

Business needs become measurable objectives, then numbered requirements and rules that a developer can build and QA can test.

What I do

  • Set objectives with a KPI, a baseline, a target and an owner
  • Write the BRD and get it signed off, including what is out of scope
  • Write the SRS to ISO/IEC/IEEE 29148, with field-level validation and messages
  • Express complex logic as business rules and decision tables
  • Prioritise with MoSCoW, and log open issues instead of guessing

Techniques

  • KPI definition
  • MoSCoW
  • Decision tables
  • Feasibility analysis
  • Cost-benefit
  • NFRs (ISO 25010)

What it produces

Phase 03

Design the solution with the team

I don't throw requirements over a wall. I work through the architecture, data and screens with tech leads and designers.

What I do

  • Define system design with PMs and tech leads: context, containers and integrations
  • Draw user flows, sequence diagrams and state machines for the hard paths
  • Model data with an ERD and a data dictionary
  • Design wireframes, and full UI with Google Stitch or Claude + Figma MCP when a project has no designer
  • Review the OpenAPI contract against the requirements it implements

Techniques

  • C4 model
  • UML sequence & state
  • BPMN-style flows
  • ERD
  • Wireframing
  • API design review

What it produces

Phase 04

Run delivery in sprints

Requirements only matter if they ship. I run the backlog and the ceremonies, and I guard the scope.

What I do

  • Break scope into epics and INVEST user stories with Gherkin acceptance criteria
  • Run backlog refinement, sprint planning, reviews and retrospectives
  • Set milestones and release plans, and track progress in Jira, Azure DevOps or Zoho Sprints
  • Allocate tasks and bugs across development, design, QA, DevOps and SEO
  • Size every change request for scope, effort and timeline before it enters a sprint

Techniques

  • Scrum
  • Story mapping
  • Estimation
  • Definition of Ready and Done
  • RAID management
  • Change control

What it produces

Phase 05

Prove it works before anyone signs

I own UAT. Every acceptance criterion becomes a test, and the client signs off against business scenarios, not a demo.

What I do

  • Review the test strategy and test cases against the acceptance criteria
  • Test APIs in Postman before the UI is ready
  • Write UAT plans and scripts, and run UAT sessions with real users
  • Triage defects with QA and developers, and decide what blocks a release
  • Keep the traceability matrix current so nothing ships untested

Techniques

  • Boundary-value analysis
  • Decision-table testing
  • API testing
  • UAT
  • Defect triage

What it produces

Phase 06

Ship, learn and feed it back

Go-live is a milestone, not the finish line. What production teaches us goes straight back into the requirements.

What I do

  • Coordinate deployments, go-live checks and release notes
  • Write incident reviews: blameless, with a timeline, 5 Whys and corrective actions
  • Turn every lesson into a change request with new tests
  • Track objectives against their baselines after launch
  • Recommend enhancements from client pain points and market value

Techniques

  • Root-cause analysis (5 Whys)
  • CAPA
  • KPI tracking
  • Roadmapping
  • Enhancement proposals

What it produces

Sprint day 1Sprint planning

Goal, scope and capacity agreed; every story meets the Definition of Ready.

Daily · 15 minStand-up

Blockers surface early, and I answer requirement questions on the spot.

Stories split, estimated and given testable acceptance criteria.

Working software shown to the client; feedback becomes stories or change requests.

Sprint endRetrospective

What to keep, change and try, with actions tracked to closure.
